## Purpose and scope

This SOP describes the tasks necessary to generate, test, implement, and approve a database set-up for a study to ensure accurate, reliable, complete, and secure electronic data.

This SOP is applicable to all study databases requiring set-up at the RI-MUHC and to those personnel responsible for database set-up, such as all Data Management and Information Technology (IT) personnel, unless otherwise stated in the study contract or Data Management Plan.

---

## Responsibilities

The **Sponsor-Investigator or QI/Investigator, Data Management personnel, and IT Systems Support personnel** (when applicable) are responsible for ensuring that database system set-up meets all applicable regulatory, ICH-GCP, Sponsor, and local requirements.

---

## Procedure

### 5.1 Prerequisites

**5.1.1** Before beginning database build:
- CRF designs must be finalized and approved → [SOP-CR-100](/sops/cr-100)
- The Data Management Plan (DMP) must be finalized and approved → [SOP-CR-103](/sops/cr-103)
- The protocol must have been finalized and REB-approved → [SOP-CR-102](/sops/cr-102), [SOP-CR-007](/sops/cr-007)

### 5.2 Database design and build

**5.2.1** Build the study database according to the CRF designs ([SOP-CR-100](/sops/cr-100)) and the DMP ([SOP-CR-103](/sops/cr-103)). Each CRF field must be accurately represented in the database with the appropriate data type, validation rules, and field label.

**5.2.2** At the RI-MUHC, REDCap is the supported electronic data capture platform for studies with ≤1,000 variables → [SOP-CR-014](/sops/cr-014). For larger or more complex databases, consult the Clinical Research Hub.

**5.2.3** Build the database in a test environment first. The production database must not be opened for data entry until all testing is complete and sign-off obtained.

### 5.3 Audit trail

**5.3.1** Configure the database audit trail to capture:
- All data entries, edits, and deletions
- The user identifier (individual-level, not shared accounts)
- Date and time of each action
- The original value, the new value, and the reason for change (where applicable)

**5.3.2** The audit trail is a regulatory requirement and cannot be disabled at any time.

### 5.4 User access controls

**5.4.1** Implement role-based access controls:

| Role | Access level |
|---|---|
| Data entry user | Enter and edit data in assigned CRFs; cannot view other participants or fields outside their scope |
| Data manager | Enter, edit, query, and resolve data; run validation checks; view all data |
| Statistician | Read-only access to de-identified data after database lock |
| Auditor/inspector | Read-only access to complete study data for audit purposes |
| System administrator | Database configuration, user management, backup management |

**5.4.2** All users must be uniquely identified; shared user accounts are prohibited.

**5.4.3** Document all user accounts, access levels, and dates of access grant and removal.

**5.4.4** Remove access immediately when a team member leaves the study or is undelegated from the Task Delegation Log.

### 5.5 Validation testing (User Acceptance Testing)

**5.5.1** Complete User Acceptance Testing (UAT) before opening the database for participant data entry. UAT must include:
- Verification that all CRF fields are correctly represented
- Testing of all data validation rules (range checks, required fields, cross-field logic)
- Testing of the audit trail
- Testing of user access restrictions (each role can and cannot access the appropriate areas)
- Testing of data export functionality

**5.5.2** Document all UAT test cases, expected results, actual results, and whether each test passed or failed. Resolve all failed tests before production launch.

**5.5.3** Retain all UAT documentation in the TMF.

### 5.6 Production launch

**5.6.1** After successful UAT and documented sign-off by the Sponsor-Investigator or delegated data manager, open the production database for data entry.

**5.6.2** Notify all data entry personnel of the database launch and provide training as needed. Document training on the Task Delegation Log.
